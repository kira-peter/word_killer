# LSServer Code Review

## 唯一判定标准

仓库根目录 `GUIDES.md` 是 Code Review 的统一代码质量标准。开始审查前必须完整读取 `GUIDES.md`；全部 Common 规则始终纳入核验，专用域规则按变更的实际影响判定是否适用。预期行为通过 `Common-Correctness-R001` 纳入核验：

- finding 必须命中 `GUIDES.md` 中一个或多个有效规则 ID。
- 只引用规则 ID 和标题，不复制规则原文。
- 报告中的每个规则 ID 都必须按“规则 ID 跳转链接”格式输出，使其可直接跳转到 `GUIDES.md` 中对应规则。
- `Common-Correctness-R001` 的证据优先级：① 对应 OpenSpec；② 无 OpenSpec 时，变更已附带的显式需求 / 任务描述（PR、任务单、提交说明中可定位的行为约定）。二者皆无则跳过 R001 行为核验，不臆造需求；源码、调用方和测试仍可作为其他规则的证据。`AGENTS.md` 仅用于下述 OpenSpec 流程检查及理解流程上下文，历史评审只用于理解上下文。
- 外部资料与 `GUIDES.md` 冲突时，以 `GUIDES.md` 为 Review 判定依据，并在“标准覆盖缺口”中记录冲突。
- 与已确认预期行为不符映射 `Common-Correctness-R001`；可证明但无法映射到更具体规则的确定性实现错误使用 `Common-Correctness-R002`；其他抽象风险放入“标准覆盖缺口”，不得用空泛最佳实践包装成 finding。

## 规则 ID 跳转链接

- 完整读取 `GUIDES.md` 时，同时记录每个规则标题所在的当前行号；生成报告前重新核对所有实际引用的规则 ID 与行号，禁止硬编码行号。
- 报告中凡出现有效规则 ID（包括 finding 标题、规则范围、已接受的偏离与例外、弱一致性观测及正文引用），均使用 Markdown 链接：`[规则 ID](GUIDES.md#L规则标题行号)`。链接文字只包含规则 ID。
- 默认采用 Cursor / VS Code 兼容的仓库根目录相对路径与单行锚点，例如 `[Common-Async-R001](GUIDES.md#L104)`。不得使用标题 slug、行号范围或外部仓库 URL 替代该格式。
- 链接后照常书写规则原始标题，例如：`[Common-Async-R001](GUIDES.md#L104) 权威业务内存只在 MainWorker 写；异步仅可进行弱一致性标量观测`。
- 不要用反引号包裹链接。若输出载体不渲染 Markdown，链接源码仍须保留；不得退化为只有规则 ID 而没有目标位置。

## OpenSpec 流程合规

Code Review 须独立核对 `AGENTS.md` 的 OpenSpec 门禁，但流程问题不映射为 `GUIDES.md` finding，也不评 finding 严重程度：

1. 按变更实际影响判断是否触发 OpenSpec，不采信 commit / PR 标注的“bugfix”“优化”等名称代替判断。
2. 触发时须存在与本次变更对应的 change，并按 `AGENTS.md` 检查 proposal、design、tasks 是否齐全、范围是否覆盖实际改动；仅当当前 OpenSpec 工作流或变更类型要求 delta spec 时再检查其完整性。仅有目录或无关 change 不算通过。
3. 未触发时记录“不需要 OpenSpec”及依据；边界无法确定且会影响设计或验收判断时，要求补充变更分类依据后再给合并结论。
4. 应有 OpenSpec 但缺失、产物不完整或与实现范围不符时，记录为“流程阻塞”，不得用 PR 描述替代流程门禁；R001 仍可按其证据优先级独立核验已有行为依据。
5. 运行 `openspec list --json` 检查未归档 change；若与本次变更对应的 change 状态为 `complete`（全部 tasks 已完成）但仍位于 `openspec/changes/<change-name>/`，记录为“流程阻塞：已完成但未归档”，要求按 OpenSpec archive 流程归档后再合并。仅规划产物齐全但 tasks 未全部完成不视为“已完成”。

流程合规结果影响合并结论：通过或确认不需要时不阻塞；流程阻塞默认判“修复或补证后可合并”；若缺少该变更按流程应提供的 design / delta spec，导致数据结构、线程模型、跨模块方案或验收边界无法安全判断，则判“不建议合并”并要求先补齐 OpenSpec 后重新审查。

## 推荐项偏离与架构契约

### 推荐规则偏离

- `[推荐]` 允许因明确的业务或架构理由偏离。Reviewer 须查找与当前变更关联、可定位且可追溯的理由记录，如 OpenSpec、PR 描述或代码注释。
- 理由足以说明偏离的必要性并覆盖该规则防范的风险时，不形成 finding，列入“已接受的偏离与例外”；没有记录或理由不能覆盖风险时形成 finding。
- 规则 ID、适用范围、替代保障和清理计划仅用于辅助判断理由是否充分，缺少其中某一项不能单独形成 finding。finding 严重程度仍按实际触发条件、影响面和可恢复性判定。

### 已有架构契约例外

- 已有架构契约是仓库内可定位、受版本控制且可核验的正式约定，如 OpenSpec spec / design、架构文档，或由 API 注释与测试共同固定的框架契约。
- 契约只有明确当前改动的适用范围、需维持的不变量、相对规则的例外边界和核验方式时，才能作为规则例外；存量实现、调用惯例、历史反例和口头共识均不构成契约。
- 契约有效且覆盖当前改动时，不形成 finding，列入“已接受的偏离与例外”；不满足上述条件时仍按 `GUIDES.md` 判定。契约与 `GUIDES.md` 存在无法解释为既有例外的冲突时，以 `GUIDES.md` 为准，并记录“标准覆盖缺口”。

## 弱一致性标量观测记录

- 本次变更新增或直接诱发的异步弱一致性标量观测，若用于业务排序、资格判定、状态推导、筛选或其他业务决策，须按 `Common-Async-R001` 完整核验。
- 只有仓库内可定位依据已明确接受陈旧值、`null` / 默认值及多字段组合不一致，且访问安全性、刷新或纠偏机制与业务不变量均核验通过时，才在报告“已确认的弱一致性观测”中单独记录。记录至少包含：位置与真实异步执行器、读取的实体和字段、结果用途、明确接受的不一致范围、刷新或纠偏机制，以及对应 Spec、设计、测试、API 注释或调用链契约依据。
- 若调用链推导证明弱一致结果会破坏业务不变量，或缺少足以证明业务已明确接受该结果的依据，按 `Common-Async-R001` 形成 finding。
- 同一观测只能归入一处：形成 finding 后不得再列入“已确认的弱一致性观测”；已确认的弱一致性观测不是 finding，也不列入“已接受的偏离与例外”。
- 仅用于日志、指标、耗时统计等、不参与业务决策且不会触发业务状态修改的标量观测可不记录。与本次变更无关的存量观测仍遵守审查边界，不纳入报告。

## 审查边界

1. 以用户指定的 PR、commit、分支、diff 或文件为准。
2. 用户未明确范围时：
   - 工作区有变更：审查 staged、unstaged 和相关 untracked 文件。
   - 工作区干净：审查当前分支相对默认基线分支的 merge-base diff。
3. 只报告本次变更新增或直接诱发的问题。相关旧代码可作为调用链证据，但不得把既有问题归责于本次变更。
4. Code Review 默认只读，不修改代码、不提交、不创建 PR；用户明确要求修复时再进入实现流程。

## 审查流程

### 1. 建立变更地图

- 获取完整 diff、改动文件和必要的提交上下文。
- 执行 OpenSpec 流程合规检查，记录是否触发、关联 change、产物完整性、任务完成状态和归档状态。
- 识别涉及的入口、Service、Manager、DAO、Entity、协议、配置、异步 Operation、生命周期和跨服链路。
- 识别本次变更新增或直接诱发、且会参与业务决策的异步弱一致性标量观测，建立待核验清单。
- 读取改动上下文及关键调用方/被调用方，不能只看 diff 片段。
- 按 `Common-Correctness-R001` 证据优先级收集预期行为：有对应 OpenSpec 则读取 proposal、design、tasks，以及该变更按流程应提供的 delta spec；无 OpenSpec 则仅采用变更已附带的显式需求 / 任务描述；二者皆无则记录“已跳过 R001 行为核验”，不臆造需求。对已采用的依据独立验证其声明。

### 2. 建立规则适用集合

- 所有审查均核验 `GUIDES.md` 的全部 Common 规则，不因改动规模或任务名称缩减通用规则范围。
- 按变更入口、调用链和实际影响判定专用规范是否适用：活动对应 Activity；大世界 / AOI / 战斗对应 World；跨服对应 CrossServer；Web / GM / 支付对应 Web。
- 沿调用链跨模块时，同时检查链路涉及模块的专用规范。
- 调查发现新的线程、资产、持久化、安全或跨服影响时，立即更新核验重点并重新判定专用域适用范围；不得因初始文件范围窄而漏掉跨切面规则。
- 建立“规则范围”记录：明确全部 Common 均已核验，并列出实际适用的专用域及判定依据；调查中范围变化时同步更新。不得只写“已核验适用规则”或“全部规则”等不可复核表述。
- 注意规则的强制度与 finding 严重程度是两个不同维度。

### 3. 逐条验证

对疑似问题至少完成以下验证：

- 定位可执行路径和触发条件。
- 跟踪真实线程边界；不得仅凭类名猜测 MainWorker 或异步上下文。
- 对业务决策相关的异步标量观测，逐项核对 `Common-Async-R001` 的访问条件与业务可接受性；仅有明确接受依据且全部核验通过者形成“已确认的弱一致性观测”，不可接受或无法证明已接受者形成 finding，二者不得重复记录。
- 跟踪输入校验、状态修改、持久化、发奖/扣费和客户端反馈顺序。
- 若已收集到 R001 依据，核对实现是否覆盖其主流程、错误路径与验收条件；已跳过 R001 时不因“缺少需求文档”或个人预期单独形成 finding。
- 核对实体归属、配置来源、协议语义、serverId 语义及机器人参与口径。
- 检查框架/工具 API 的真实实现，确认返回值、异常、回调线程和副作用。
- 必要时运行最小范围编译、测试或静态检查，区分“已验证”与“未验证”。

证据不足时继续调查；无法证实时不报告 finding。不要报告纯猜测、偏好差异或没有实际影响的风格问题。

### 4. 形成 finding

每条 finding 必须同时具备：

1. 至少一个准确的规则 ID，并引用该规则在 `GUIDES.md` 中的原始标题。
2. 可在 IDE 中跳转的仓库相对路径与当前 diff 行号，并附可定位符号。
3. 可复现的触发条件或完整调用路径。
4. 具体影响，不使用“可能有问题”之类空泛表述。
5. 与根因对应的最小修复方向。

同一根因造成的多处表现合并为一条；不同根因不要混写。按严重程度降序输出。

## IDE 跳转代码位置

报告中的源码位置必须优先适配 Cursor / VS Code：

1. 使用仓库根目录相对路径，禁止只写文件名、Java 包名或不可移植的本机绝对路径。
2. 位置字段使用 Markdown 本地文件链接，链接文字保留 IDE 可识别的 `path:line`：
   `[\`relative/path/File.java:123\`](relative/path/File.java#L123)`。
3. 每条 finding 的主要问题位置紧跟一个 Cursor 代码引用块，格式参照下方输出模板：三个反引号后直接写
   `startLine:endLine:relative/path/File.java`；代码块中至少包含一行当前源码，不加语言标记。
4. 同一 finding 有多个位置时，每个位置都使用本地文件链接；只为理解根因所需的关键位置添加代码引用块，避免复制大段代码。
5. 输出前重新读取或搜索目标文件，核对路径和当前行号；不得沿用过期 diff 行号。无法可靠取得行号时使用可跳转文件链接并附符号名，不得编造行号。
6. 若输出载体不支持 Cursor 代码引用，仍保留 Markdown 本地文件链接及 `relative/path/File.java:line` 文本作为 VS Code 等 IDE 的降级格式。

## Finding 严重程度

`GUIDES.md` 的 `[强制]` / `[推荐]` / `[参考]` 是 Agent 开发代码时采用规则的强度；本节等级是
Code Review 对具体 finding 实际影响的评级，两者相互独立：

- `[强制]` 违规不自动判高，[推荐] 违规也不自动判低；均依据触发条件、影响面和可恢复性评级。
- `[参考]` 不作为硬约束，不能单独形成 finding；若已证明存在实际缺陷，须映射到其他适用规则。
- 合并结论由 findings 的实际影响决定，不由命中的规则强度直接决定。

- **致命**：可稳定造成严重数据损坏、重复 / 丢失高价值资产、全服不可用或可直接利用的安全问题。
- **高**：主流程可触发的数据错误、MainWorker 阻塞、越权、跨服不一致或无法安全恢复。
- **中**：特定条件下触发的功能错误、持久化遗漏、错误反馈或明显性能退化。
- **低**：影响有限但确实违反规则的可维护性或可观测性问题。

## 合并结论

合并结论不机械映射最高严重程度，而根据未解决问题是否必须处理、能否局部修复及当前证据是否足以确认安全：

- **可合并**：OpenSpec 流程检查通过或确认不需要，且没有未解决 finding；必要的编译、测试或静态检查已完成，或未验证项已说明且不影响本次变更的安全判断。已接受的偏离 / 例外和标准覆盖缺口本身不阻塞合并。
- **修复或补证后可合并**：存在可通过补齐 OpenSpec 产物解决的流程阻塞；存在必须处理但可在当前方案内局部修复的 finding；或实现未发现确定性问题，但缺少影响合并判断的必要验证证据。完成修复 / 补证并重新核验后方可合并。
- **不建议合并**：OpenSpec 关键设计缺失导致高风险方案无法安全判断；存在致命问题，或高风险问题涉及不可逆数据 / 资产损坏、可利用安全缺陷、全服可用性、无法安全恢复；或多个问题共同表明核心设计、线程模型、数据模型或迁移方案需要重做，不能靠局部修复收敛。

只要仍有未接受的 finding，不得给出“可合并”。同为高 / 中 / 低级 finding 时，须结合修复范围和可恢复性选择“修复或补证后可合并”或“不建议合并”，并在结论中说明依据。

## 输出格式

先给结论，再给 findings。不要用表格堆叠长文本。

````markdown
## 结论

[可合并 / 修复或补证后可合并 / 不建议合并]。一句话说明最高风险、修复 / 补证范围和审查范围。

## 流程合规

- OpenSpec：[不需要 / 已通过（change 名称）/ 流程阻塞]
- 依据：触发或豁免条件、产物完整性、任务完成与归档状态，以及实际改动覆盖范围

## 规则范围

- 已核验：全部 Common 子类，以及实际适用的专用域
- 依据：变更入口、调用链和风险横切面；审查中适用范围的变化及触发原因

## Findings

### [高][Common-Async-R002](GUIDES.md#L112) MainWorker 同步查询数据库

- 规则：[Common-Async-R002](GUIDES.md#L112) 禁止在 MainWorker 上执行阻塞 I/O
- 位置：[`relative/path/File.java:123`](relative/path/File.java#L123)（`methodName`）

```123:126:relative/path/File.java
// 至少包含一行能够定位问题的当前源码
```

- 触发：从入口到问题点的实际调用路径与条件
- 影响：可观察、具体的后果
- 建议：最小可执行修复方向

## 已接受的偏离与例外

- `[规则 ID](GUIDES.md#L规则标题行号)`：记录位置、适用范围及接受依据

## 已确认的弱一致性观测

- 位置/执行器：[`relative/path/File.java:123`](relative/path/File.java#L123)（异步执行器或调用链）
- 观测：读取的实体与标量字段；结果用途
- 明确接受范围：允许的陈旧值、`null` / 默认值及多字段不一致
- 纠偏与依据：刷新机制，以及明确接受该范围的 Spec / 设计 / 测试 / API 注释 / 调用链契约证据

## 验证

- 已执行：命令或核验动作及结果

````

标准覆盖缺口不属于 finding，不单独影响合并结论；没有覆盖缺口时省略该章节。

没有已接受的推荐项偏离或架构契约例外时，省略“已接受的偏离与例外”。

没有命中记录条件且通过 `Common-Async-R001` 核验的业务决策型弱一致性观测时，省略“已确认的弱一致性观测”。
